# Подключение Telegram к платформе ФСП

Бот и его привязка намеренно не реализованы. Приложение работает без токена и без доступа к Telegram. Готовы таблица очереди, поле привязки и интерфейс отправителя в `backend/src/notifications.ts`.

## Что уже есть

Каждое внутреннее Notification создаётся вместе с OutgoingDelivery в той же транзакции. Доставка содержит `channel=TELEGRAM`, `status=PENDING`, attempts, nextAttemptAt, deliveredAt, lastError. Запись без привязанного чата остаётся в ожидании и не расходует попытки.

Функция `deliverPending(sender, limit=25)` выбирает ожидающие записи и вызывает переданный `ExternalSender`. Успех означает DELIVERED. Ошибка увеличивает счётчик, назначает повтор с экспоненциальной задержкой до часа; после пяти попыток — FAILED. Функция нигде автоматически не вызывается: это точка подключения будущей команды.

Формат аргумента sender:

```ts
interface DeliveryMessage {
  deliveryId: string;
  notificationId: string;
  userId: string;
  telegramChatId: string | null;
  event: string;
  title: string;
  body: string;
  href: string; // относительный URL SPA
}
```

События: WELCOME, REGISTRATION_OPEN, APPLICATION_SUBMITTED, APPLICATION_STATUS, COACH_REQUEST, COACH_LINK, JUDGE_ASSIGNED, PROTOCOL_PUBLISHED, PROTOCOL_UPDATED, COMPETITION_CANCELLED, DEADLINE, EXPIRY. Notification.role указывает целевой кабинет. Уведомления кабинета скрываются при переключении в другую роль; будущий бот должен включать название целевого кабинета и проверять актуальность роли получателя.

## Порядок реализации

1. Создать бота через BotFather. Передавать `TELEGRAM_BOT_TOKEN` только в backend/worker, через окружение. Добавить `PUBLIC_APP_URL` для абсолютных ссылок. Токен не помещать в frontend, Git или журналы.
2. Реализовать серверную генерацию случайного одноразового токена привязки для авторизованного пользователя. В БД хранить хеш, userId, срок около 10 минут и время использования; нужна отдельная миграция.
3. В профиле добавить «Подключить Telegram» со ссылкой `https://t.me/<bot>?start=<token>`. При `/start` атомарно проверить токен и сохранить chat.id в User.telegramChatId. Никогда не привязывать чат по одному userId или email из входящего сообщения.
4. Включить отвязку и при необходимости повторную привязку через подтверждение. User.telegramChatId уникален. Проверять, что обновление пришло из Telegram: webhook secret или long polling; выбрать один способ.
5. Реализовать ExternalSender через Telegram Bot API sendMessage. Отправлять title, body и кнопку на `PUBLIC_APP_URL + href`; текст отправлять без parse_mode или экранировать его. Обрабатывать 429 с retry_after, недоступный чат и блокировку бота.
6. В отдельном процессе с одним worker вызывать `deliverPending` каждые несколько секунд, не допуская перекрытия вызовов. Для нескольких worker сначала добавить атомарный claim записей с блокировкой, lease и восстановлением после падения. Текущая заготовка рассчитана на один worker.
7. Не отправлять накопившиеся WELCOME/устаревшие события после привязки: добавить выборку по дате привязки или явную политику TTL. Сейчас дата привязки ещё не хранится. После удаления роли не отправлять уведомления этой роли.
8. Добавить экран состояния привязки, отвязку, контроль ошибок FAILED и возможность ручного повторения федерацией. Не давать пользователю просматривать чужую очередь.

## Гарантии и ограничения

Доставка имеет семантику «как минимум один раз»: если Telegram принял сообщение, а процесс упал до сохранения deliveredAt, повтор может дублировать сообщение. События дедуплицируются внутри платформы уникальным Notification.dedupeKey; это не гарантирует отсутствие дублей у внешнего API. Не отмечать запись доставленной до успешного ответа Telegram.

Минимальная ручная проверка после подключения: связать два разных аккаунта с двумя чатами, убедиться в адресности; отправить смену статуса заявки; проверить повтор после ошибки и FAILED; отвязать аккаунт; проверить просроченный и повторно использованный токен. До завершения этих работ внешний канал не считать реализованным требованием кейса.
